# Human Answer Telegram Bot

Telegram бот для пересылки сообщений между пользователями.

## Описание

Этот бот позволяет пользователям отправлять текстовые сообщения, которые будут пересылаться случайным образом другим пользователям. После получения ответа, он будет направлен обратно отправителю.

Проект имеет архитектуру с отдельным веб-бэкендом, который предоставляет API и веб-интерфейс для просмотра всех диалогов, а Telegram бот является опциональным интерфейсом к этому бэкенду.

## Особенности

- Пересылка текстовых сообщений между пользователями
- Случайный выбор получателей (с исключением пользователей, занятых диалогом)
- Правило «одно сообщение — один ответ»
- Хранение информации о пересылках
- Поддержка команд /start и /help
- Многоязычность (текущая реализация на русском)
- Веб-интерфейс для просмотра всех диалогов
- API для интеграции с другими системами
- Возможность имитации пользователей через веб-интерфейс
- Поддержка работы с пользователями и их сообщениями через API

## Логика работы

Ядро поведения бота — **«одно сообщение — один ответ»**. Ниже описаны термины и
правила, которые реализуются в `src/services/messageBusinessService.js` и
`src/services/telegramChatService.js`.

### Термины

| Термин | Значение |
| --- | --- |
| **Непрочитанное сообщение** | Сообщение, у которого `replied = FALSE`, то есть получатель ещё не ответил |
| **Ждёт ответа** (awaiting) | У пользователя есть отправленное им сообщение с `replied = FALSE` |
| **Занятой пользователь** (busy) | У пользователя есть непрочитанное входящее сообщение |
| **Ответ** | Новое сообщение, у которого заполнен `reply_message_id` |

### Правило 1. Ответ на входящее разрешён всегда

Если у пользователя есть непрочитанное входящее сообщение, его сообщение
всегда трактуется как **ответ** последнему непрочитанному (`handleMessage`).
Новое сообщение при этом не создаётся.

> **Почему так.** Иначе возникает тупик: Алиса ждёт ответа от Бориса, Кэрол
> пишет Алисе, и Алиса уже не может ответить Кэрол, а Кэрол — ей. Ответы
> должны быть доступны всегда.

### Правило 2. «Одно сообщение — один ответ»

Если пользователь **ждёт ответа** на своё ранее отправленное сообщение, то
**новое сообщение отправить нельзя** — ни случайному получателю, ни выбранному
вручную. Дождаться ответа необходимо.

Текст ошибки: `Вы уже отправили сообщение пользователю X и ещё не получили ответ.`

### Правило 3. Занятые пользователи не получают новых сообщений

Если пользователь **занят** (не ответил на полученное сообщение), то:

- он **исключается из пула** случайных получателей;
- отправка ему **вручную отклоняется** с текстом
  `X ещё не ответил на полученное сообщение — новые сообщения ему не отправляются`;
- в веб-интерфейсе он помечен в списке получателей значком `🚫`.

Как только пользователь отвечает, он снова становится доступным.

> **Важно.** Это правило **не применяется к ответам**. Ответ занятому
> пользователю разрешён и обязателен — иначе он не смог бы освободиться.

### Порядок проверок (случайный режим, `handleMessage`)

1. Есть непрочитанное входящее → **ответ** отправителю.
2. Нет входящих, но есть ожидающие ответа → **отказ** (правило 2).
3. Нет входящих и нет ожидающих → **новое сообщение** случайному получателю
   из свободных (правило 3).

### Порядок проверок (ручной режим, `sendMessageToUser`)

1. Отправитель ждёт ответа → **отказ** (правило 2).
2. Есть непрочитанное входящее:
   - от от выбранного получателя → сообщение считается **ответом** ему,
     исходное помечается `replied = TRUE`;
   - от другого пользователя → **отказ**: сначала ответьте ему.
3. Выбранный получатель занят → **отказ** (правило 3).
4. Иначе → сообщение отправляется выбранному получателю.

### Как отправляется ответ

Ответ сохраняется как **отдельная запись** в таблице `messages`, связанная с
исходным сообщением через `reply_message_id`. Исходное помечается
`replied = TRUE`.

Это принципиально: если просто обновить `replied`, текст ответа был бы потерян
и переписка не была бы видна в интерфейсе. В веб-интерфейсе ответ отображается
с цитатой исходного сообщения.

### Схема статусов

```
Отправитель                          Получатель
───────────                          ───────────
отправил ──► ждёт ответа ──(ответ)──► свободен
    ▲                                     │
    └────────────(новое сообщение)────────┘

Занятой (есть непрочитанное входящее):
    не получает новых сообщений ни случайно, ни вручную,
    но может и обязан ответить → становится свободным
```

## Установка

1. Клонируйте репозиторий:
```bash
git clone <repository-url>
cd human-answer-tgbot
```

2. Установите зависимости:
```bash
npm install
```

3. Создайте Telegram бота через BotFather и получите токен

4. Добавьте токен в файл `.env`:
```
TELEGRAM_BOT_TOKEN=ваш_токен_бота
```

5. Запустите сервер:
```bash
npm run server
```

6. Для запуска Telegram бота отдельно:
```bash
npm start
```

> **Внимание:** скрипт `npm start` ожидает файл `src/index.js`, который сейчас
> отсутствует в репозитории. Основной рабочий сценарий — `npm run server`
> (веб-бэкенд с API и интерфейсом). Логика бота при этом доступна и
> используется веб-интерфейсом.

## Демонстрация

Для запуска демонстрации с 10 пользователями и более 30 парами вопрос-ответ:

```bash
# Запуск демонстрации (может занять несколько минут из-за рандомных задержек)
npm run demo
```

**Примечание**: Скрипт создает много сообщений с рандомными задержками для имитации реального поведения пользователей. Процесс может занять от 2 до 5 минут в зависимости от производительности системы.

- `src/` - Исходный код бота
  - `backend/` - Веб-бэкенд с API endpoint'ами
  - `bot/` - Логика работы с Telegram API (опциональный интерфейс)
  - `database/` - Работа с базой данных

## Команды бота

- `/start` - Начать работу с ботом
- `/help` - Показать справку

## Веб-интерфейс

После запуска сервера доступны две страницы:

| Адрес | Назначение |
| --- | --- |
| `http://localhost:3001/` | Все диалоги системы |
| `http://localhost:3001/users.html` | Мессенджер: переписки по пользователям + отправка от их имени |

Порт можно изменить переменной окружения `PORT` (по умолчанию `3001`).

Страница `users.html` предназначена для проверки поведения бота: в ней видно,
какое правило сработает до отправки, а получателя можно оставить случайным
(поведение бота) или выбрать вручную.

## API

Все ответы возвращаются в формате `{ success: boolean, data?: any, error?: string }`.

### Сообщения
- `POST /api/message` - Отправить сообщение от имени пользователя.
  Тело: `{ userId, messageText, receiverId? }`.
  Если `receiverId` указан — сообщение уходит конкретному пользователю,
  иначе работает бот-логика (ответ / случайный получатель).
  Нарушение правил возвращается как `409` с текстом ошибки.
- `GET /api/dialogs` - Получить все диалоги
- `GET /api/dialog/:senderId/:receiverId` - Получить историю диалога
- `GET /api/user-messages/:userId` - Все сообщения пользователя (отправленные и полученные)

### Пользователи
- `GET /api/users` - Список пользователей. Для каждого дополнительно
  возвращаются счётчики `sent_count`, `received_count`, `unread_count`
  (непрочитанные входящие) и `awaiting_reply_count` (ждёт ответа).
- `POST /api/register` - Зарегистрировать пользователя.
  Тело: `{ userId, username?, firstName?, lastName? }`

## Локализация

Все текстовые сообщения вынесены в отдельные файлы в `src/locales/`. Это позволяет легко добавлять поддержку других языков в будущем.
